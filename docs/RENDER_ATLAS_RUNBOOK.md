# ClientVerse Production Runbook: Render and MongoDB Atlas

## Purpose

This runbook provisions the verified ClientVerse Docker image as one Render Web Service and connects it to a managed MongoDB Atlas cluster. The production process keeps all credentials in provider secret managers, creates no fictional demo CRM data, and uses the application health endpoint for release verification.

## 1. Create MongoDB Atlas First

Create an Atlas project named **ClientVerse Production**, then create a production cluster in **AWS N. Virginia** so it is close to the selected Render Virginia service. Create a least-privilege database user that has only the rights ClientVerse needs on the `clientverse` database. Generate the application connection string and store it only in the Render secret manager as `MONGO_URL`.

Atlas network access must permit the Render application's outbound connection according to the provider's current guidance. Do not use an unrestricted database user or store the Atlas URI in Git, a browser field visible to ordinary users, or client-side code. Enable the Atlas backup plan before customer records are created, and test a restore into an isolated recovery environment before launch.

## 2. Create the Render Service

In the authorized Render workspace, create a Blueprint from the repository branch `manus/premium-crm-completion`, using `render.yaml`. Render builds the root `Dockerfile`, serves the React SPA and FastAPI API from one origin, and checks `/api/health`. The configuration intentionally uses Render's `starter` plan as the minimum recommended initial web-service class; confirm the provider's current price before creating the paid service.

The Blueprint requires values for the secret-managed fields. Complete all required values before the first production deploy:

| Variable | Required production value |
|---|---|
| `MONGO_URL` | Atlas connection string for the least-privilege production database user. |
| `ADMIN_EMAIL` and `ADMIN_PASSWORD` | Initial owner administrator credentials held only in Render secrets. |

`JWT_SECRET`, `WEBHOOK_CRON_SECRET`, and `INTEGRATION_ENC_KEY` are generated by Render from the Blueprint. For the first deploy, ClientVerse uses Render’s runtime `RENDER_EXTERNAL_URL` as its same-origin public URL and CORS allowlist. After binding a custom domain, set `FRONTEND_URL`, `CORS_ORIGINS`, and `PUBLIC_BACKEND_URL` together to the final HTTPS origin. Google and Stripe variables are intentionally omitted from the Blueprint until approved provider accounts and test credentials are ready; the CRM truthfully exposes those integrations as requiring configuration.

## 3. Domain and Scheduler

Deploy first to Render's generated HTTPS domain. After the health and authenticated smoke tests pass, bind the approved custom domain and update `FRONTEND_URL`, `CORS_ORIGINS`, and `PUBLIC_BACKEND_URL` together. Re-run the smoke tests after the domain change.

Create scheduled work only after the web service is healthy. The existing commitment-risk endpoint requires the `WEBHOOK_CRON_SECRET`, validates a run identifier for idempotency, and must never be exposed as an unauthenticated public task. Use UTC schedules and record the exact schedule, endpoint, and service owner in the operations record.

## 4. Post-Deploy Acceptance

Verify `/api/health`, authenticate the production administrator, create and retrieve a controlled tenant-scoped record, confirm cross-tenant denial, and run the browser smoke sequence. Check that `SEED_DEMO_DATA=false` resulted in an empty operational tenant, except for the deliberately configured administrator account. Only then connect Google or Stripe credentials and perform their separate lifecycle certifications.
